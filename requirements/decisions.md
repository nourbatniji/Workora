MVP · Oct 1, 2026 · @trendow

This log records the decisions that shape the MVP build. SRS v1.2 (Oct 3, 2026) applies D-01 to D-03, so `srs.md` and this log agree. If they differ again, the decision here wins until `srs.md` is updated.

Status values:

- **Agreed**: decided by the product owner.
- **Agreed (SRS)**: already fixed in the consolidated SRS; listed here so the build has one place to check.
- **Proposed**: an implementation choice made for the development plan; becomes Agreed once accepted.
- **Open**: still to decide. Working assumptions are in `assumptions.md`.

| D-72 | Payroll rules in a settings version: the lateness policy is `{ mode: 'exact' }` or `{ mode: 'tiered', bands }`, each band `{ fromMinutes, toMinutes (null = and more), dayFraction (0–1) }`, at most 10. **Bands:** whole minutes, both ends included (16–60 covers 16 and 60); no gaps (each band starts one minute after the previous one ends); the last band must be open-ended. **Minutes:** late minutes are counted from shift start (BR-1), early-leave minutes back from shift end (BR-2). | D-73 | Check-in settings in the settings version (the shift date's version applies, D-70): check-in window 0–240 minutes before shift start; check-out window 30–720 minutes after shift end (shown in hours, default 6). **Check-out window replaces the 2-hour rule:** check-out is accepted until shift end + check-out window, and the day is labelled only when that window closes (SRS FR-AT-2, FR-AT-4, BR-4, D-38), so no employee check-out can arrive after a Missing check-out exception exists; a later check-out is refused with "Ask your Admin to add it". **Corrections (FR-AT-5, FR-EX-5)** recalculate the day with the same version. A pending exception is recalculated in place; one whose label disappears closes as resolved; a new label creates a new pending exception. **Decided exceptions are never changed, and amounts are never applied twice:** a day has at most one original exception per type (unique attendance record + type). When a correction changes a type that already has a decided exception, the system creates one pending **adjustment** linked to it (`adjusts_exception_id`) for only the difference: new calculated amount − amount already applied, where already applied = the approved final amount plus approved adjustments (rejected = 0; converted to leave = 0 EGP, and the leave already taken is not changed). Example: overtime approved for 2 hours, corrected to 3 hours → the adjustment is for the 1 unpaid hour, not another 3 hours. **Negative adjustments:** if the correction lowers the amount, the adjustment reverses only the over-applied part: overtime approved for 3 hours, corrected to 2 → an adjustment of −1 hour (a deduction line); lateness deducted for 60 minutes, corrected to 20 → a refund of the 40-minute difference (an addition line). A type's total never changes sign (overtime never below 0, deductions never above 0), and late + early totals stay within the daily cap (D-72). Approving an adjustment brings the type's total to the new amount; rejecting it keeps the old total; the Admin may edit it. A type has at most one pending adjustment: a newer correction recalculates it in place. Corrections and decisions take the same attendance-day lock (D-72), so two at once cannot both apply. **Payroll:** each exception and adjustment enters payroll exactly once (it records its `payroll_run_id` once, and a payroll line references it uniquely). | D-74 | Setup wizard progress is one JSON column, `companies.setup_steps` (default `{}`), mapping each step to `done` or `skipped`; a step not in it is still to do; unknown keys are ignored.
